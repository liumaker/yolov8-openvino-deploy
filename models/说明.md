# 模型与产物说明

这条流水线里的模型是同一张网络的三种"皮"，一层层换格式：

```
models/yolov8n.pt                      PyTorch 权重（Ultralytics 格式，fp16 存储，6.25 MB）
  └─ scripts/export_onnx.py    →  models/onnx/yolov8n_640_b1.onnx    ONNX（fp32，12.26 MB）
                                 models/onnx/yolov8n_640_dyn.onnx    ONNX 动态形状（12.47 MB）
  └─ scripts/export_ir.py      →  models/ir/yolov8n_640_b1_fp32.xml + .bin   OpenVINO IR
                                 models/ir/yolov8n_640_b1_fp16.xml + .bin   OpenVINO IR（权重 fp16）
```

## 1. 静态 ONNX 与动态 ONNX

- **静态**（本例）：输入锁死 `[1,3,640,640]`，输出锁死 `[1,84,8400]`。推理引擎可以提前把
  内存布局、算子融合、线程切分全部算死，速度上限最高；代价是换分辨率就得重导，喂 480×640 会直接报
  `InvalidArgument: Got invalid dimensions for input`。
- **动态**：输入是 `[batch, 3, height, width]`，输出前两维仍固定为 `84`、第三维是 `anchors`
  （随输入尺寸变）。灵活，但多了一条 `Shape → Gather → Unsqueeze → Concat → Reshape` 的形状计算链
  （234 → 322 个节点），每个尺寸都要重新算，速度略低。

`84 = 4 + 80`：4 个框坐标 (cx, cy, w, h)，80 个 COCO 类别分数。YOLOv8 是 anchor-free 的，
**没有 objectness 分支**，所以不是 85。`8400 = 80² + 40² + 20²`，对应 stride 8/16/32 三个特征图
的网格点总数；输入 480×640 时是 60×80 + 30×40 + 15×20 = 6300。

## 2. 各种 json 是谁写的

- Ultralytics 的元数据（`names`、`task`、`imgsz`、`stride`、`license` 等）是**嵌在 ONNX 文件内部**的
  `metadata_props` 里，不是旁边另生成一个文件。商用前请留意 `license = AGPL-3.0`。
- `models/onnx/*.meta.json`、`models/ir/*.ir.json`、`models/ir/*.verify.json` 都是**本项目脚本**
  写出来的验收报告（结构、算子直方图、数值误差），删掉不影响推理。

## 3. OpenVINO IR 是什么

IR = Intermediate Representation，由两个文件组成，必须成对使用：

- `.xml`：纯文本，描述计算图（节点、连接关系、每条边的形状和精度）；
- `.bin`：二进制，存权重和偏置。

`ov.convert_model()` 做的事：解析 ONNX → 翻译成 OpenVINO 的 nGraph 表示 → 常量折叠/算子融合/
形状推断 → `ov.save_model()` 序列化。命令行等价的写法是：

```bash
ovc models/onnx/yolov8n_640_b1.onnx --compress_to_fp16=False -o models/ir
```

## 4. "FP16 IR" 的真相（重要）

`ov.save_model(..., compress_to_fp16=True)` **只把权重压成 fp16，计算仍然是 fp32**。
转换后 fp16 版多出 131 个 `Convert` 节点，就是权重在 fp16→fp32 之间来回转换的痕迹：

| 版本 | .bin | 节点数 | 说明 |
|---|---|---|---|
| fp32 | 12.71 MB | 402（非 Constant 240） | 权重原始 fp32 |
| fp16 | 6.35 MB | 533（多 131 个 Convert） | 权重存 fp16，读入后转 fp32 计算 |

所以在 **CPU** 上，fp16 IR 省的是磁盘和内存带宽，算力并不会翻倍，甚至可能因为多了 Convert 而略慢；
真正的 FP16 加速要 Intel GPU（iGPU/dGPU）。这个结论正好可以放进 benchmark_app 的对比里。
节点总数不能拿来和 ONNX 的 234 直接比——ONNX 的 initializer 在 IR 里会变成 `Constant` 节点
（本例 160 个），扣掉后是 240 个真正的计算节点。

## 5. 数值验收（`scripts/verify_ir.py`）

同一张图、同一套 letterbox、同一个 float32 张量，分别喂 ONNX 与两份 IR，比较原始输出：

| 对比 | max\|Δ\| | 相对误差 | 判定 |
|---|---|---|---|
| fp32 IR vs ONNX | 2.045e-03（框 2.04e-03 / logits 2.00e-06） | 3.21e-06 | PASS |
| fp16 IR vs ONNX | 3.181e+00（框 3.18e+00 / logits 3.31e-03） | 4.99e-03 | PASS |

框坐标的绝对误差看着大，是因为输出已经乘过 stride、量级到 600+；用**相对误差**判断才对。
fp16 的误差主要落在框坐标上（约 0.5%），对检测结果基本无影响，后面量化时还会看到更明显的对比。
